# Kasada / KPSDK — 有状态客户端挑战与信任边界

> 复现对象：`spider research/其他/pro53 kasada` · 技术分类：`waf` `vm` `env` · 状态：📄 仅思路（不提供直接复现）

## 产品与目标

- 防护产品：Kasada（公开指纹：`x-kpsdk-*` 阶段响应头、`KPSDK` 全局对象、两段 UUID 形式的挑战资源路径）
- 触发形态：A 类首访 429 挑战页；B 类首访 200，正常页面下后台运行传感器并写入会话
- 分析目标：多个授权测试实例（分属电商、零售、地产、酒店等行业；不记录真实域名、IP、UA、Cookie 值与脚本哈希）
- 研究范围：挑战状态机、检测面、客户端/服务端信任边界，以及“会话复用”与“逐请求校验”的差异

## 技术要点

- 客户端：大体积混淆 VM + PoW/加密 bundle + 环境指纹采集；挑战通过后由脚本写入会话 cookie
- 服务端：以阶段响应头标记挑战进度；会话按实例绑定请求画像，并可能要求逐请求派生头
- 两种起点：429 挑战型要真解挑战；200 传感器型只需等待会话建立——200 不代表没有 Kasada
- 复用语义：会话 cookie + 匹配的请求画像通常足够；手工伪造派生头会破坏一致性并触发拒绝
- 与纯签名 WAF 的区别：有状态、分阶段，按画像与风险评分决定挑战强度，而不是单点验签

## 思路摘要

- 入口：阶段响应头 / `KPSDK` 全局对象 → 挑战脚本 → 挑战参数与回执 → reload → 会话
- 观察：同一挑战资源被多个实例共享；阶段标记会在 reload 后从“挑战中”转为“已建立”
- 分析方法：网络时间线、响应头与会话写入时序、浏览器与 HTTP 客户端对拍、逐 URL 差分（概念）
- 关键结论：多数实例仅凭会话 cookie 即可复用；少数实例逐请求校验；个别实例卡在出口/画像风险评分，而非挑战算法
- 边界：纯算法还原不现实（VM + PoW + 逐请求派生）；高对抗实例需要真实浏览器与风险画像

## 防御启示

- 挑战完成不等于可信：服务端应复算会话、请求画像、时间与派生头的一致性，风险评分只作辅助信号
- 短 TTL + 逐请求 nonce 能提高重放成本；分阶段挑战可按画像分级，降低正常用户摩擦
- 同族实例共享挑战资源降低维护成本，但会扩大单点泄露/单点绕过的影响，需版本隔离与灰度回滚
