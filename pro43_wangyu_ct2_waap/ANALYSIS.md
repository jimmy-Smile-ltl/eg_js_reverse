# 网御星云 CT2-WAAP 挑战架构与信任边界

> 本文只讨论产品形态、挑战阶段与防御启示，不提供完整可执行客户端；关键实现仅以去密钥/去实例值的示意片段出现，不可直接运行。不含真实域名/UA/Cookie/密钥/脚本哈希或绕过步骤。

## 1. 产品指纹

| 观察点 | 结论 |
|--------|------|
| 响应头 | `Server: CT2-WAAP` |
| 首次访问 | 412 `Environment Checking` 挑战页 |
| 挑战失败 | 进入 NWAF 拦截页，说明 CT2-WAAP 与 NWAF 是两层不同的防护 |
| 资源形态 | 挑战页加载混淆脚本；脚本存在慢速下发/自校验等保护 |
| 传输层 | 未观察到 TLS/JA3 是主要门槛；凭证与 HTTP 层一致性更关键 |

## 2. 挑战阶段

```text
首次请求
  → 412 Environment Checking
  → 加载挑战脚本
  → 客户端采集环境信号
  → 生成多类短时凭证（环境判定 / 查询 / 指标）
  → 设备身份由服务端登记
  → 刷新页面
  → 服务端校验“设备 + 凭证 + 时间窗 + 请求一致性”
  → 放行或进入 NWAF 拦截页
```

关键点：这不是“算一个签名就结束”的挑战，而是**有服务端状态的设备登记流程**。

## 3. 凭证职责拆分

从行为上可以观察到凭证至少承担四类职责：

| 职责 | 作用 | 设计含义 |
|------|------|----------|
| 环境判定 | 表达本次浏览器环境是否可信 | 把客户端风险评分编码进凭证 |
| 查询准入 | 绑定脚本版本与时间窗 | 防止旧脚本/旧凭证长期复用 |
| 设备身份 | 标识已登记设备 | 服务端保存登记表，而不是只做校验和 |
| 指标上报 | 记录交互/环境统计 | 为风控评分提供额外信号 |

> 具体 Cookie 名称、明文结构、密钥与时间窗参数不在本文展开。

## 4. 服务端信任边界

| 客户端能提供的 | 服务端真正能验证的 | 可被绕过的点 |
|----------------|-------------------|--------------|
| 环境分数、WebDriver 标志 | 凭证格式、时间戳、设备登记状态 | 客户端分数本身不可全信 |
| UA、语言、屏幕等 | UA 与凭证/会话的一致性 | 仅改 UA 不一定够 |
| 设备 UUID | UUID 是否在登记表中 | 纯离线造号无法通过登记 |
| 请求时间 | 凭证时间窗是否新鲜 | 短 TTL 降低重放价值 |

设计上最有价值的是**设备登记制**：即使攻击者能复原凭证格式，只要设备身份没有被服务端登记，仍然无法通过。这比单纯校验客户端分数更接近“有状态信任”。

## 5. 分析方法的合规边界

原始分析中使用过 Cookie setter 观察、关键函数静态提取、CDP 断点与路由拦截等手段。这些方法本身属于动态分析技术，但本文只保留方法论层面的结论：

- 先观察“谁写了什么”，再定位加密/签名调用；
- 先做行为对拍，再决定是否值得静态解混淆；
- 服务端边界要通过篡改实验确认，而不是从客户端逻辑猜测。

**不提供**：完整 Hook 客户端、bundle 补丁、密钥、Cookie 值、设备号、脚本哈希与可直接运行的请求链。

### 5.1 关键实现脚本/片段（示意）

> 只保留凭证字段形状与处理顺序；标签、密钥、设备号、脚本哈希全部省略，代码不可直接运行。

```python
# 示意：环境凭证 / 查询凭证的字段结构
def build_env_credential(ts, device_id, risk, verdict, key, iv):
    plain = "&&".join(["002", str(ts), ENV_LABEL, device_id,
                       str(risk), verdict, str(ts)[-2:]])
    return b64(AES_CBC_PKCS7(plain, key, iv))

def build_query_credential(ts, nonce, script_hash, key, iv):
    plain = "&&".join(["002", str(ts), QUERY_LABEL, nonce,
                       script_hash, str(ts)[-2:]])
    return b64(AES_CBC_PKCS7(plain, key, iv))

# 示意：服务端需要同时验证的状态
def server_accepts(env_cred, query_cred, device_id, now, ua, script_hash):
    env = open_credential(env_cred)
    query = open_credential(query_cred)
    return (env.device_id == device_id
            and device_registered(device_id)
            and fresh(env.ts, now) and fresh(query.ts, now)
            and query.script_hash == script_hash
            and ua_consistent(env, ua))
```

关键环节：

| 环节 | 关键内容 | 安全含义 |
|------|----------|----------|
| 环境采集 | WebDriver/headless/图形/时序信号 | 评分输入，客户端可影响 |
| 设备登记 | 设备标识进入服务端登记表 | 形成有状态信任 |
| 凭证生成 | 环境/查询分离 + 短 TTL | 降低重放价值 |
| 服务端校验 | 设备、时间、UA、脚本版本 | 可独立复算的一致性 |

## 6. 防御启示

1. **不要把客户端风险分当作唯一信任依据**：客户端可以伪造分数，服务端应复算关键一致性。
2. **有状态设备登记优于无状态校验和**：登记表 + 短时凭证能显著提高离线伪造和重放成本。
3. **凭证职责拆分**：环境、查询、指标分开，避免一个凭证泄露后全线失守。
4. **一致性校验比单点检测更重要**：UA、语言、设备、时间窗、脚本版本之间要相互约束。
5. **隐私与可访问性**：过度采集 WebGL/Canvas/Audio/字体等环境信号会带来合规、兼容与误伤风险。
6. **分层防护**：挑战层之后仍有 NWAF 语义引擎；人机挑战不是全部安全能力。

## 7. 结论

CT2-WAAP 的核心不是“某个固定算法”，而是**环境采集 + 设备登记 + 短时凭证 + 服务端一致性校验**的组合。对研究者的价值在于理解这种有状态信任模型；对 defenders 的价值在于知道哪些信号可以采信、哪些必须服务端复算。
